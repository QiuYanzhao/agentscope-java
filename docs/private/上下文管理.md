# Harness 上下文管理（重构笔记）

> 原文：<https://java.agentscope.io/v2/zh/docs/harness/context>
> 重构目标：快速建立设计思想 + 架构分层 + API 速查，应对面试。

---

## 1. 它解决什么问题

Agent 跑一个长任务（读代码、改文件、跑测试）时，每轮都要把"用户要什么、做过什么、工具刚返回了什么"喂给模型。任务越长，这些内容越多，要么爆上下文窗口，要么烧钱。

Harness 的核心做法一句话：**每次请求模型之前，重新组装一遍发给模型的内容**，而不是任务开始时拼一次 prompt 然后一直沿用。组装时同时做三件事：

1. 加载该带的材料（静态指令、动态业务数据、任务状态）；
2. 计算预算，先省可选项，再压缩历史；
3. 超长时把大结果卸到文件里，按需回读。

`ReActAgent` 本身也能跑，但不会自动装这套策略；`HarnessAgent` 默认开启。

## 2. 核心心智模型（面试必背）

先分清三个经常被混在一起的东西：

| 概念 | 是什么 | 生命周期 |
|---|---|---|
| `AgentState` | **持久化的工作状态**：会话历史、Todo、计划模式、权限规则、tool state | 跨 call 保存，按 `(userId, sessionId)` 寻址 |
| `RuntimeContext` | **per-call 调用元数据袋**：userId、sessionId、requestId、DB 连接、审计 logger | 每次调用 new 一个，不持久化 |
| **实际发给模型的 prompt** | 从 `AgentState` + 工作区文件 + 动态来源**当场组装**出来的本轮输入 | 每轮推理重新生成，不存回历史 |

关键认知：`RuntimeContext` 里的属性**不会自动**变成模型提示；`AgentState` 里存的历史**也不会原样**全发给模型——中间隔着一层"组装"。

### 组装顺序（四层）

每次推理前，Harness 按下面顺序拼好这一轮给模型看的内容：

| 顺序 | 层 | 内容 | 例子 |
|---|---|---|---|
| 1 | **System** | 合并后的稳定指令、项目规则、模式规则 | AGENTS.md、`instruction(...)`、工作原则、环境信息 |
| 2 | **对话历史** | 用户消息、Assistant 消息、工具调用与结果；过长时带摘要 | 已读过的代码、刚才的测试输出 |
| 3 | **当前状态** | 从 Todo / 计划 / 动态来源生成的临时消息 | `TASK_STATE`、`RUNTIME_STATE`、最新构建状态 |
| 4 | **参考材料** | 工作区记忆、知识文件、动态参考资料 | MEMORY.md、检索片段、项目文档约定 |

工具 Schema 随请求单独提供，也占预算。第 3、4 层是临时组织出来的，**不会每轮重复追加到持久化历史**。

## 3. 静态规则：`instruction` 与 AGENTS.md

**是什么**：稳定的角色和行为规则，进入 System 层。

两种放法：
- 工作区文件 `AGENTS.md`（人格、行为约定）；
- Builder 上挂 `instruction`（可信的业务指令）。

```java
builder.instruction("test-policy", "修改代码后运行相关测试；无法运行时说明原因。");
```

**边界**：
- 工作区材料在**一次 call 开始时加载**。执行期间改了 `AGENTS.md`，本次调用不会变，下次才生效。
- 想让业务数据在工具执行后立刻刷新？别用静态文件，用下面的动态来源。

---

## 4. 动态业务数据：`contextSource`

**是什么**：你在 Builder 上注册一个回调，Harness 在**每次准备发给模型的请求时**调用它，把返回的内容作为第 3 层（当前状态）或第 4 层（参考材料）拼进 prompt。

```java
builder.contextSource("build-status", request -> Mono.just(List.of(
    ContextBlock.runtime("latest", "当前构建：测试失败，登录模块有 2 项失败。")
)));
```

### ContextBlock 的两种类型

| 工厂方法 | 用途 | 预算行为 |
|---|---|---|
| `ContextBlock.runtime(id, text)` | 当前事实：构建状态、审批进度、剩余额度 | 作为当前状态展示 |
| `ContextBlock.reference(id, text)` | 参考资料：检索片段、文档约定 | 预算紧张时可被省略 |

`reference` 还能挂版本和优先级：

```java
builder.contextSource("project-guide", request -> Mono.just(List.of(
    ContextBlock.reference("login", "登录接口约定：会话过期返回 401。")
        .withRevision("guide-v3")
        .withPriority(20)
)));
```

### 关键行为（面试点）

- **`build()` 时不执行**；每次推理请求准备时才调用。
- 回调拿到的 `ContextRequest` 带 `agentId / userId / sessionId / callId / purpose`，可据此查数据并鉴权。
- **超时默认 5 秒**；失败策略默认 `FAIL`（直接报错停掉这轮）。可有可无的材料改成 `OMIT`：

```java
builder.contextSource("related-notes",
    request -> Mono.just(List.of(ContextBlock.reference("note", "历史排查记录"))),
    options -> options.timeout(Duration.ofSeconds(2)).onFailure(SourceFailurePolicy.OMIT));
```

### 边界（容易踩坑）

- 回调必须**只读、幂等、线程安全**——一次执行可能准备多轮请求，回退重试也会再调。
- **不要**在回调里扣费、下单、写业务数据。
- 动态来源**不能当 System 指令**用；要稳定规则用 `instruction`。
- `OMIT` 不会沿用上次旧值，失败就是失败。
- 把内容标为参考材料、设优先级，**都不能替代权限检查**——来源内部仍要按 userId/sessionId 鉴权。

## 5. 长程任务跟进：Todo 工具

> ⚠️ **勘误**：官方文档 v2 站点提到的 `TaskContextOptions` / `TaskContextState.beginTask()` / `VerificationService` / `allowRequirementProposals()` 在当前源码中**尚未实现**，本节只讲真实可用的部分。

**是什么**：`enableTaskList()`（默认 **OFF**）开了之后，框架做两件事：
1. 注册 `todo_write` 工具——**由模型自己在 ReAct 循环里调用**，应用不参与；
2. 装一个 `TaskReminderMiddleware`——每轮 reasoning 之前把当前 todo 列表重新渲染成 `<system-reminder>` 注入 prompt。

```java
ReActAgent.builder()
    .name("planner")
    .model(model)
    .enableTaskList()   // 一行开关，默认 OFF
    .build();
```

### `todo_write` 的语义

- **全量替换**：模型每次传入完整 todo 列表，不是增量 patch。框架拿新列表整个重建 `AgentState.tasksContext`。
- 每项三个字段：`content`（描述）、`status`（`pending` / `in_progress` / `completed`）、`priority`（可选 high/medium/low）。
- **不变量**：全局最多只能有一个 `in_progress`，工具会直接拒绝违反的调用。
- 内容相同的旧任务会保留 id 和 createdAt，避免全量重写导致身份漂移。

模型典型调用长这样：

```json
{ "todos": [
  {"content": "定位登录失败原因", "status": "in_progress", "priority": "high"},
  {"content": "修改鉴权中间件",   "status": "pending"},
  {"content": "跑回归测试",       "status": "pending"}
]}
```

### 状态怎么被模型看到

- Todo 列表持久化在 `AgentState.tasksContext`（类型 `TaskContextState`，就是个 `List<Task>` 包装，没有 `beginTask` 之类的方法）；
- `TaskReminderMiddleware` 每轮 reasoning 前把它渲染成系统提醒——所以即使早期对话被摘要压掉，模型仍看得到当前进度；
- 应用**没有**"设置任务目标"的 API。任务目标就是模型根据用户消息自己拆解出来的 todo；你想影响它，只能在 `sysPrompt` / `AGENTS.md` 里写规则。

### 配合 Plan Mode

先想清楚再动手时结合 Plan Mode：计划文件存完整方案，Todo 跟踪执行步骤。框架**不会**自动把 `PLAN.md` 段落拆成 Todo，二者靠 Agent 自己维护。

## 6. 上下文体积治理：三层防线

Harness 默认全开，按"先便宜后昂贵"的顺序处理。

### 第一层：大工具结果卸载（Tool Result Eviction）

一次测试输出几兆日志，直接塞 prompt 太浪费。Harness 的做法：

- **默认阈值 80,000 字符**；超过的工具结果写到工作区 `large_tool_results/` 下，上下文里只留**首尾各 2,000 字符预览 + 文件路径**；
- 模型要看细节自己调 `read_file` 分段读。

```java
builder.toolResultEviction(ToolResultEvictionConfig.builder()
    .maxResultChars(40000)
    .previewChars(1000)
    .build());
```

`read_file / write_file / edit_file / memory_* / session_search` 本身不参与卸载。

### 第二层：预算分配（ContextPolicy）

处理完大结果后，按预算裁材料。**裁剪顺序**（从先到后）：

1. 省可选的记忆 / 知识材料；
2. 省其他可选参考材料；
3. 保留 System 和 `required` 块；
4. 剩下的空间才给对话历史。

```java
builder.contextPolicy(new ContextPolicy(
    24000,   // 最大输入预算
    4096,    // 为模型输出预留
    1024,    // 安全余量
    ContextTokenEstimator.approximate(),
    manifest -> { /* 观察回调，见第 8 节 */ }
));
```

模型没报告窗口大小时，输入预算**回退到 64,000 token**。估算不是供应商精确计数，含图片时尤其要留余量。

### 第三层：历史压缩（Compaction）

选定材料后，处理对话历史。顺序：

1. **先做不用模型的轻量处理**：裁剪旧的大块工具输出；
2. 仍超预算，**再调模型**把早期对话总结成摘要，保留近期消息。

```java
builder.compaction(CompactionConfig.builder()
    .triggerMessages(30)   // 默认 50 条消息触发检查
    .keepMessages(10)      // 保留最近 10 条（keepTokens=0 时生效）
    .build());
```

- 摘要默认用 Agent 主模型，可换辅助模型；自定义 `summaryPrompt` 必须保留 `{messages}` 占位符。
- 压缩会维护工具调用与结果的配对，不会把一次工具交互从中间切开。

### 超预算怎么办

发请求前做最终检查。如果 System + 必需材料还是塞不下，抛 `ContextBudgetExceededException`。

压缩没禁用时，框架会**在同一次执行里自动强制压缩并重试这一轮一次**——不会重新提交用户任务，也不会把已执行的工具从头再跑一遍。重试还失败才把错误抛给调用方。

## 7. 三个"历史"的分工（面试极易混）

| 东西 | 用途 | 什么时候读 | 会不会被摘要掉 |
|---|---|---|---|
| **压缩后的工作历史** | "接着做" | 每轮推理 | 会，早期被总结成摘要 |
| **长期记忆 Memory** | "以后还值得记住" | 每次 call 加载为参考材料；也可被工具查询 | 独立维护，不参与对话摘要 |
| **完整 Session Log** | "回看当时发生了什么" | 应用排查、恢复会话时按 API 读 | 不删，只追加 |

关键结论：
- 压缩**只改变模型继续工作看到的内容**，不会删 Session Log；
- 摘要和记忆提取都可能漏细节，**不能拿摘要当完整记录**；
- Todo / 计划模式 / 权限等结构化状态独立保存，不会被当普通对话摘要掉。

## 8. 诊断工具：ContextManifest

模型好像没看到某条信息时，用 Manifest 查这一轮到底准备了什么、用了多少预算、哪些被省了。它是 Harness 自动生成的**上下文构建清单**，只含元数据（不含提示词正文），不需要业务代码自己构造。

**注意粒度**：一次 `agent.call()` 可能经历多轮推理和工具执行；**每准备一次模型请求就产生一个 Manifest**。要查的是出问题的那一轮，不是整个任务的最后一条。

### 在 Builder 上挂观察回调

最直接的方式是在构建 Agent 前给 `ContextPolicy` 配一个回调。它和预算配置是同一份 `ContextPolicy` 对象：

```java
import io.agentscope.harness.agent.context.ContextManifest;
import io.agentscope.harness.agent.context.ContextPolicy;
import io.agentscope.harness.agent.context.ContextTokenEstimator;

builder.contextPolicy(new ContextPolicy(
        24000,                                   // ① 最大输入预算
        4096,                                    // ② 为模型输出预留
        1024,                                    // ③ 安全余量
        ContextTokenEstimator.approximate(),     // ④ token 估算器
        (ContextManifest manifest) -> {          // ⑤ 每轮上下文构建完的回调
            System.out.printf("call=%s purpose=%s validation=%s tokens=%d/%d%n",
                    manifest.callId(), manifest.purpose(), manifest.validation(),
                    manifest.estimatedInputTokens(), manifest.inputLimit());
            manifest.items().forEach(item -> System.out.printf(
                    "  source=%s revision=%s placement=%s%n",
                    item.sourceId(), item.revision(), item.placement()));
            manifest.transforms().forEach(change -> System.out.println("  " + change));
        }));
```

**`ContextPolicy` 前四个参数**（和第 6 节预算配置是同一份）：

| 位置 | 参数 | 含义 |
|---|---|---|
| ① | `maxInputTokens = 24000` | 整个模型请求的输入预算上限 |
| ② | `outputReservation = 4096` | 给模型输出预留的空间 |
| ③ | `safetyMargin = 1024` | 安全余量（应对估算误差） |
| ④ | `estimator` | token 计数方式，`approximate()` 是近似估算 |

**⑤ Manifest 回调里每个字段是什么**：

| 字段 | 含义 |
|---|---|
| `callId()` | 这一次**模型请求**的 ID（不是 sessionId / turnId / runId） |
| `purpose()` | 这次请求的用途（普通推理 / 摘要 / 记忆提取等） |
| `validation()` | 构建结果：`passed` / `budget_exceeded` / `invalid_tool_pairs` / `state_conflict` / `history_conflict` / `build_failed` |
| `estimatedInputTokens()` / `inputLimit()` | 估算输入量 / 最终可用上限；不是供应商账单实际 token 数 |
| `items()` | 这一轮保留下来的材料清单。`sourceId` 定位来源（如 `source/project-guide/login`），`revision` 是版本，`placement` 是放在 prompt 的哪一层 |
| `transforms()` | 构建过程中做过的处理：`tool_result_offload`（大结果卸载）、`history_compaction`（历史压缩）、`omitted_for_budget:...`（因预算被省）、`source_unavailable:...`（OMIT 来源读失败） |

**回调注意事项**：
- 共享 Builder 时这个回调也被复用，**必须线程安全、尽快返回**；
- 生产环境别在回调里做耗时 IO，把元数据丢给观测系统（Micrometer / OTel）异步处理；
- 已自定义过 `contextPolicy` 时，替换要保留原数值和 estimator，只换回调，别把预算参数冲掉。

### 在事件流里拿

已经在消费 `streamEvents` 的话，不用额外调一次 Agent，直接在现有事件流里监听名为 `context_build` 的 `CustomEvent`，载荷里取 `context_manifest` 字段即可。原生 Session Log 会把它存为 `context/build` 记录，事后排查某个会话时通过 `session.log()` 读回。

### 排查顺序

先看 `validation()` 和预算，再按 `sourceId()` 找具体材料——

| 现象 | 含义 |
|---|---|
| `items()` 里有目标 source，`validation=passed` | 材料这轮确实送进去了，问题在内容本身或指令是否清晰 |
| `transforms()` 里出现 `omitted_for_budget:source/...` | 因预算不足被省了，调短材料、调大预算或调优先级 |
| `transforms()` 里出现 `source_unavailable:...` | 配置为 `OMIT` 的来源读失败，查数据源或超时 |
| 两种都没有 | 来源可能返回空列表，或这轮根本不该加载它 |
| `validation=build_failed` 且 token 数为 `-1` | 构建过早失败，Manifest 还没统计完，看抛出来的异常 |

Manifest 只存元数据，**不能用来重放提示词或恢复会话**；sourceId 可能含文件名，导出诊断日志时注意脱敏。

## 9. 面试速查

### 关键默认数字

| 项 | 默认值 |
|---|---|
| 大工具结果卸载阈值 | 80,000 字符 |
| 卸载后预览保留 | 首尾各 2,000 字符 |
| 动态来源超时 | 5 秒 |
| 模型未报告窗口时的输入预算 | 64,000 token |
| 历史压缩触发消息数 | 50 条 |
| 旧工具输出保护窗口 | 约 40,000 token |
| 旧工具输出裁剪阈值 | 累计约 20,000 token |

### 高频考点

1. **Harness 上下文管理和裸 ReActAgent 的区别？**
   ReAct 循环一样，但 Harness 额外装了：材料加载、任务状态展示、预算控制、大结果卸载、历史压缩。

2. **`RuntimeContext` 和 `AgentState` 的区别？**
   前者是 per-call 瞬态元数据（userId/requestId/连接），后者是跨 call 持久化的工作状态（历史/Todo/权限）。

3. **`contextSource` 什么时候被调用？能干嘛？**
   每次准备发给模型的请求时调；返回 `ContextBlock.runtime`（当前事实）或 `ContextBlock.reference`（参考资料）；不能当 System、必须只读幂等。

4. **上下文变长时 Harness 的处理顺序？**
   先卸载大工具结果 → 再按预算裁可选材料 → 再裁剪旧工具输出 → 最后调模型做对话摘要；还超就抛异常，压缩开启时自动重试一次。

5. **摘要、长期记忆、Session Log 三者关系？**
   摘要给模型"接着干"，记忆给以后的会话"记住这事"，Session Log 给人"回看全程"。谁也不替代谁。

6. **`enableTaskList` 到底开了什么？谁来写 todo？**
   两件事：注册 `todo_write` 工具（模型自己全量替换待办列表）+ 装 `TaskReminderMiddleware`（每轮 reasoning 前把列表重新注入 prompt）。todo 内容和状态都是模型自己维护的，应用没有"设置任务目标"的 API。
